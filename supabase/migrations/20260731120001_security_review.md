# Auditoria de Segurança (SAST) — Etapa 1: Database & RLS

## Veredicto: APROVADO para prosseguir

### Controles implementados

| Controle OWASP | Implementação |
|---|---|
| M2 Insecure Data Storage | Sem secrets no schema; tokens ficam no Auth/SecureStore no client |
| M3 Insecure Auth | Todas as policies amarradas a `auth.uid()` |
| API1 Broken Object Level Auth | `cellar_wines` exige `user_owns_cellar(cellar_id)` |
| API3 Broken Object Property Auth | CHECK constraints em capacity, quantity, vintage, alcohol |
| API4 Unrestricted Resource Consumption | Tabela + função `check_rate_limit` (service_role) |
| Injection | Funções com `SET search_path = public`; inputs normalizados/limitados |
| Privilege Escalation | `FORCE ROW LEVEL SECURITY`; `anon` sem grants; wines_cache write só service_role |

### Achados e mitigações

1. **IDOR em cellar_wines** — Mitigado: policy não usa `user_id` enviado pelo client; valida ownership da adega.
2. **Cache poisoning em wines_cache** — Mitigado: authenticated só SELECT; INSERT via Edge Function + Zod + service_role.
3. **Rate limit bypass** — Mitigado: função `SECURITY DEFINER` só concedida a `service_role`.
4. **Trigger privilege** — `handle_new_user` é DEFINER com `search_path` fixo; não aceita input arbitrário além de `auth.users`.
5. **Trigram DoS** — `search_wines_cache` limita query (2–200 chars) e `LIMIT` máximo 20.

### Residual / aceito

- `wines_cache` é legível por qualquer usuário autenticado (intencional: cache global de fichas públicas de vinho, sem PII).
- Limpeza de `rate_limits` antigos deve ser feita por cron/job separado (não bloqueante nesta etapa).
